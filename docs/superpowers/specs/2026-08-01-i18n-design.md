# Lokalisierung (i18n) — Design

Datum: 2026-08-01 · Status: entworfen, vom Nutzer freigegeben (mündlich), schriftliche Prüfung ausstehend

## Ziel

Die bislang rein deutsche Oberfläche wird in fünf Sprachen nutzbar:
**Deutsch, Englisch, Französisch, Spanisch, Japanisch.** Deutsch bleibt die
Referenzfassung (die heutigen Texte). Alle Übersetzungen werden im Repo
gepflegt, nicht extern.

### Scope

**Drin:** sämtliche UI-Texte der App — Navigation/View-Namen,
Begrüßungs-/Upload-Seite inkl. Fehlermeldungen und Analysebericht,
Filter-Chips, Buch-Detailkarte, Achsen/Legenden/Tooltips/Leermeldungen der
acht Views, Abdeckungshinweise, Fußzeile, Lade-/Fehlertexte, alle
`aria-label`s. Dazu: locale-abhängiges Zahlenformat, `<html lang>`,
japanische Typografie, englische README mit neuen Screenshots.

**Nicht drin:** Datenwerte (Tags, Sammlungsnamen, Autor·innen, Buchtitel —
kommen aus dem Export), CLI-Ausgabe von `scripts/normalize.mjs`, interne
Dokumente `docs/*.md`, `CLAUDE.md`. Der Dokumenttitel „Tsundoku 積ん読"
ist Brand und bleibt in allen Sprachen gleich.

## Sprachwahl & Persistenz

- **Erkennung:** Beim ersten Besuch wird `navigator.languages` per
  Prefix-Match gegen die fünf unterstützten Locales geprüft
  (`de-AT → de`); ohne Treffer Fallback **`en`**.
- **Umschalter:** in der **Fußzeile** (erscheint auf jeder Seite —
  Begrüßung, Fehlerseite, App). Schlichtes `<select>` mit Endonymen:
  Deutsch · English · Français · Español · 日本語. Per `aria-label`
  benannt.
- **Persistenz:** localStorage (`tsundoku.locale`) wird **nur beim
  expliziten Umschalten** beschrieben. Ohne gespeicherte Wahl folgt die
  App weiter der Browsersprache; erst eine bewusste Wahl friert sie ein.
- **Nicht in der URL:** Geteilte Links bleiben sprachneutral und öffnen
  sich in der Sprache des Empfängers.
- Ein Effekt im Provider setzt `document.documentElement.lang` auf die
  aktive Locale.

## Architektur

Neues Verzeichnis `src/i18n/`, null neue Dependencies:

```
src/i18n/
  messages.ts       Messages-Interface (die eine Wahrheit über alle Schlüssel),
                    SUPPORTED_LOCALES = ['de','en','fr','es','ja'] as const,
                    Locale-Typ, Endonym-Map für den Umschalter
  de.ts             Referenzfassung: heutige deutsche Texte, 1:1 übernommen
  en.ts fr.ts es.ts ja.ts   je ein Messages-Objekt, typisiert gegen das Interface
  detect.ts         detectLocale(stored: string | null, navigatorLangs: readonly string[]): Locale
                    — pure Funktion: gespeicherte Wahl gewinnt, sonst Prefix-Match,
                    sonst 'en'
  LocaleContext.tsx  Provider + Hook useI18n(): { m: Messages; locale: Locale;
                    fmtInt: (n: number) => string; setLocale: (l: Locale) => void }
```

**Konventionen für das Interface:**

- Gegliedert nach App-Bereichen (`nav`, `upload`, `report`, `filter`,
  `detail`, `views.shelf`, `views.timeline`, …, `footer`, `app`).
- Texte mit Platzhaltern, Zählungen oder Pluralformen sind **Funktionen**
  (`tooLarge: (mb: number, limitMb: number) => string`). Jede Sprache
  formuliert frei — Japanisch ohne Plural, Französisch mit eigenen
  Regeln; keine ICU-Syntax, gut korrekturlesbar.
- Fehlende Übersetzung oder toter Schlüssel = Compile-Fehler (fünf
  Objekte gegen ein Interface).
- Geschätzt 150–200 Schlüssel; alle fünf Bündel wandern in den einen
  Build (~15–25 kB unkomprimiert, kein Lazy-Loading).

## Sonderfälle

1. **Sprachnamen** (`src/lib/languages.ts`): Die handgepflegte
   `LANG_LABELS`-Tabelle wird ersetzt durch eine Map
   LibraryThing-Name → ISO-Code (`German → de`, `Greek (Ancient) → grc`, …)
   plus `Intl.DisplayNames(locale, { type: 'language' })` für die
   Anzeige. Sprachnamen in allen fünf UI-Sprachen kommen damit vom
   Browser (ドイツ語, allemand, …). Unbekannte LibraryThing-Namen fallen
   auf den Rohwert zurück. Die Sentinel-Werte `OTHER_LANG`/`UNKNOWN_LANG`
   bleiben intern unverändert (auch als `LANG_COLORS`-Schlüssel); nur ihre
   Anzeige („andere"/„unbekannt") wird ein Message-Schlüssel.
2. **Dewey-Klassen** (`DDC_LABELS`, `DDC_SHORT`) und **Medientypen**
   (`MEDIA_LABELS`): von Hand je Locale übersetzt, wandern ins
   Message-Bündel. Für Japanisch bibliotheksnahe Terminologie
   (z. B. 社会科学 für Sozialwissenschaften). `DDC_COLORS` bleibt in
   `ddc.ts`.
3. **`filterLabel`** (`src/store/filters.ts`): bekommt die Messages als
   Parameter — `filterLabel(f: Filter, m: Messages)` — statt sie zu
   importieren. Bleibt pur und testbar; `FilterChips` reicht das aktive
   Bündel durch.
4. **Zahlenformat** (`src/lib/format.ts`): das feste
   `Intl.NumberFormat('de-DE')` entfällt; `useI18n()` liefert `fmtInt`
   gebunden an die aktive Locale. `fmtYear` bleibt locale-unabhängig
   (Jahre ohne Tausendertrennung).

## Ton der Übersetzungen

| Sprache | Register |
|---|---|
| Deutsch | Du-Form (Bestand) |
| Englisch | neutral-direkt („your library") |
| Französisch | Vouvoiement (UI-Konvention) |
| Spanisch | Tuteo (übliche UI-Praxis) |
| Japanisch | です/ます-Form |

Der Begrüßungstext erklärt 積ん読 in DE/EN/FR/ES; die japanische Fassung
erklärt den Begriff nicht (das Publikum kennt ihn), sondern spielt mit ihm.

### Übersetzungs-Workflow (Phasen im Implementierungsplan)

Die Übersetzungen entstehen **nicht** beim Planschreiben und **nicht**
nebenbei durch Implementierungs-Agenten. Der Plan trennt drei Phasen:

1. **Extraktion (mechanisch, günstiges Modell):** Die heutigen deutschen
   Texte wandern in `messages.ts` + `de.ts`, die Komponenten werden auf
   `useI18n()` umgestellt. Erst hier steht die endgültige
   Schlüsselstruktur fest.
2. **Übersetzung (Spezialist, fähigstes verfügbares Modell):** Eigene
   Tasks für EN/FR/ES/JA mit ausformuliertem Übersetzungs-Brief im Plan:
   Register-Tabelle (unten), Terminologie (Dewey-Klassen,
   Diagramm-Vokabular), freie Formulierung der Funktions-Messages je
   Sprache, Behandlung von 積ん読. Das Interface erzwingt Vollständigkeit.
3. **JA-Review:** Ein separater Review-Agent prüft die japanische Fassung
   (Register, Natürlichkeit, Bibliotheksterminologie), bevor der Nutzer
   testet.

## Japanische Typografie

Lokalisierung nach Japanisch ist zusätzlich ein typographisches Problem.
Drei Schriftrollen, drei CJK-Fallbacks:

| Rolle | Latein | CJK-Fallback | Begründung |
|---|---|---|---|
| Display (View-Überschriften, große Labels) | Fraunces | **Shippori Mincho** (neu) | charakterstarke Mincho als Pendant zur Display-Serife |
| Buchtitel (Detailkarte) | Fraunces | **Noto Serif JP** (neu) | voller Zeichenvorrat — Shippori Mincho ist begrenzt, Fallback mitten im Titel wäre ein Bruch. Gilt in **jeder** UI-Sprache (Buchtitel sind Daten) |
| Body/Sans, Mono-Beschriftung | Source Sans 3 / IBM Plex Mono | Noto Sans JP (Bestand) | wie bisher |

- Der Namenszug „積ん読" im Header wird in **allen** Sprachfassungen mit
  Shippori Mincho gesetzt — der Brand ist japanisch, unabhängig von der
  UI-Sprache.
- **Optische Angleichung** als `:lang(ja)`-Block auf dem Root, der nur
  CSS-Tokens überschreibt (kein Eingriff in Komponenten): Kanji füllen
  das Geviert vollständig, lateinische Versalhöhe liegt bei ~0,7 em —
  Japanisch wirkt bei gleicher `font-size` größer; Mincho wirkt durch
  dünne Waagerechten heller. Daher: Grundschriftgröße ~0,94 em,
  Shippori einen Schnitt schwerer als das Fraunces-Pendant,
  `--line-height` von ~1,5 auf 1,8–1,9.
- **Bezug** wie die übrigen Schriften über Fontsource; die JP-Pakete sind
  per `unicode-range` in Subsets zerlegt, der Browser lädt nur benötigte
  Slices.
- **Lizenztabelle** (README) wächst um: Shippori Mincho (© FONTDASU,
  OFL-1.1), Noto Serif JP (© Google, OFL-1.1).

## README & Screenshots

Die README wird **englisch** neu geschrieben — gleiche Struktur und
Inhalte, keine parallele deutsche Fassung — mit einem Satz zur
fünfsprachigen UI. Die vier Screenshots werden mit englischer UI neu
aufgenommen. CLI-Ausgabe und `docs/*.md` bleiben deutsch.

## Tests

- `detect.ts`: Unit-Tests — gespeicherte Wahl schlägt Browser,
  Prefix-Match (`de-AT → de`), Fallback `en`, ungültiger
  localStorage-Wert wird ignoriert.
- Bestehende Tests mit deutschen Strings (`filterLabel` in
  `filters.test.ts`) erhalten das `de`-Bündel explizit als Parameter.
- Vollständigkeit erzwingt der Compiler; dazu ein Rauchtest je Locale:
  einige Funktions-Messages aufrufen, Ergebnis ist nicht-leerer String,
  kein Wurf.
- Typografie-Verifikation per Screenshot-Durchsicht der japanischen UI
  (Zeilenhöhen, Trunkierung, Namenszug, Detailkarte mit japanischem
  Buchtitel).

## Bewusste Nicht-Ziele

- Keine i18n-Bibliothek (react-i18next, Paraglide): fünf fest eingebaute,
  im Repo gepflegte Sprachen brauchen weder Lazy-Loading noch
  Übersetzer-Workflows noch ICU-MessageFormat.
- Keine Sprache in der URL, keine vier README-Fassungen, keine
  Übersetzung von Datenwerten.
